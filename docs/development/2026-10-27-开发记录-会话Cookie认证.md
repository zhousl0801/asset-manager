# 会话 Cookie 与 Passkey 认证

日期：2026-10-27。范围：把「每个请求携带明文访问口令」替换为「口令登录一次 → 服务端签名会话 Cookie」，并追加 Passkey（指纹 / Face ID）登录。

## 背景

原实现由 `ApiAccessMiddleware` 校验 `Authorization: Bearer <口令>`，前端把口令本身存进 `sessionStorage`。问题：

- 秘密存在 JS 可读存储中，XSS 即全失；每个请求重复发送口令。
- 没有会话概念：无法过期、无法收敛风险；改口令必须重启服务。
- 登录没有失败限流，公网 API 可被慢慢爆破。

同源策略已先行落地（`Serve web app from API origin`），因此可以安全使用 `SameSite=Lax` 的 Cookie，无需处理跨站 Cookie 与 CORS 凭据。

## 现状设计

| 项目 | 现值 |
| --- | --- |
| 登录 | `POST /api/access/login`，口令正确后签发会话 Cookie |
| 会话探测 | `GET /api/access/session` → `{ required, authenticated, passkeyEnabled, passkeyAvailable }` |
| 退出 | `POST /api/access/logout`，清除 Cookie |
| Cookie | `asset-keeper-access`，`HttpOnly`、`SameSite=Lax`、生产固定 `Secure`（开发环境随请求协议，便于本地 HTTP 调试）、`Path=/`，有效期 7 天、访问即续期 |
| 认证明细 | 会话票据内写入口令散列指纹；口令变更后全部旧会话立即失效 |
| 授权 | 生产环境默认要求登录（回退策略），`/api/health`、访问口令端点、静态站点与 `index.html` 显式匿名 |
| 未登录响应 | API 返回 401 JSON（不重定向），前端收到 401 后回到口令页 |
| 限流 | 登录 10 次 / 5 分钟；超出返回 429 |
| 口令存储 | `ASSET_KEEPER_ACCESS_PASSWORD_HASH`（PBKDF2-SHA256，210,000 次，16 字节盐）；未配置散列时接受 `ASSET_KEEPER_ACCESS_PASSWORD` 明文并在进程内散列一次 |

### 口令散列

格式：`pbkdf2-sha256$210000$<base64 盐>$<base64 散列>`。

生成方式（参数建议通过环境变量传入，避免进入 shell 历史）：

```sh
dotnet run --project api/src/AssetKeeper.Api -- hash-password "$NEW_PASSWORD"
```

归还的整行写入 `ASSET_KEEPER_ACCESS_PASSWORD_HASH`。轮换口令后不需要重启已有会话立即失效逻辑以外的人工操作；旧 Cookie 在下一次请求时因指纹不匹配被拒绝。

## 环境行为

- 生产：必须配置散列或口令，否则启动即失败。
- 开发：未配置口令时保持免登录（与改造前一致）；配置后启用完整登录流程，便于本地验收。
- 集成测试：`AssetKeeperApiFactory` 使用开发环境且不配置口令，保持既有 240 项行为；新增的生产模式工厂单独验证登录、401、退出、轮换与限流。

## 已知边界

- **没有服务端会话表**：退出只清除浏览器 Cookie，票据本身在 7 天内仍可被重放；需要「远程登出 / 设备列表」时再引入 `access_sessions` 表并在 `ValidatePrincipal` 中校验。
- **限流按连接来源分区**：Render 前置代理下所有请求共享代理地址，实际接近全局限流。单用户场景可接受；若将来有多用户或多实例，需按可信转发头解析真实来源。
- Cookie 使用 `SlidingExpiration`，连续使用会持续续期；闲置超过 7 天需重新输入口令。
- Passkey 挑战存在单进程内存：多实例部署需换成共享缓存；服务重启后未完成的注册 / 登录流程需要重来（已完成的会话 Cookie 不受影响）。
- 绑定自定义域名时必须显式配置 `Passkey__RpId` 与 `Passkey__Origins__0`，否则浏览器会因 RP ID 不匹配拒绝。

## Passkey（指纹 / Face ID）登录

口令仍然保留，Passkey 只是更快的登录方式。登录后进入「我的 → 登录与安全 → 在此设备启用」，由系统弹窗完成指纹 / Face ID 验证，之后登录页直接显示「使用指纹 / Face ID 登录」。

| 项目 | 现值 |
| --- | --- |
| 端点 | `POST /api/access/passkeys/registration/options|complete`（需登录）、`POST /api/access/passkeys/login/options|complete`（匿名，登录限流）、`GET /api/access/passkeys`、`DELETE /api/access/passkeys/{id}` |
| 存储 | 表 `passkey_credentials`（credential_id 唯一、public_key、sign_count、label、transports、created_at、last_used_at），一设备一条 |
| 用户标识 | 单用户固定 user handle，支持无用户名（discoverable credential）登录 |
| 挑战 | 服务端内存缓存 + `asset-keeper-passkey` 一次性 Cookie（HttpOnly、5 分钟、Path 限定在 passkeys 路由） |
| 校验 | Fido2NetLib 4.3.1；RP ID / Origins 默认取 Render 的 `RENDER_EXTERNAL_URL`，本地为 localhost（5173 / 5069） |
| 兜底 | 口令登录始终可用；删除全部 Passkey 后登录页自动隐藏 Passkey 入口 |

实现中的两个坑：

- MVC 的全局 `JsonStringEnumConverter` 会把 COSE 算法序列化成 `eS256` 这类名字，浏览器无法识别，注册会以 `NotAllowedError` 失败。Passkey 端点改为使用独立 `JsonSerializerOptions` 输出，`pubKeyCredParams.alg` 恢复为 COSE 数字（-7 / -257 等）。
- 注册完成后 `passkeyAvailable` 是启动时的旧值，退出后登录页不显示 Passkey 入口；前端改为在 `hasAccess` 变为 false 时重新探测会话。
- 右上角浮动「锁定」按钮已移除，退出登录改放在「我的 → 登录与安全」；该页面同时提供 Passkey 启用与删除。

- 手动：本地以 `ASPNETCORE_ENVIRONMENT=Development ASSET_KEEPER_ACCESS_PASSWORD=... dotnet run` 启动，确认未登录 401、错误口令 401、正确口令下发 `HttpOnly; SameSite=Lax` Cookie、`/api/access/session` 返回已登录、退出返回 204 并清除 Cookie。
