G0 的 `HistorySafety` 拒绝策略已由 G1 的事实重放替代；G0 文档中的“完整历史重算属于下一步”只描述当时阶段，不是当前待办。同样，首轮文档中的初始请求规则、迁移数量和验证数量应按 G0、G1、G2 的后续变化理解。

G2 在 G1 基础上把基金买入拆成“待确认”和“确认”两个业务事实：扣款时现金减少、待确认增加，持仓不变；确认时待确认结转份额与成本，不再扣现金。现金、待确认和已确认持仓互斥计入，历史重放按各自业务日期和顺序处理，已确认的待确认记录不能直接改金额或撤销。

赎回闭环沿用同一事实模型：申请只冻结份额，仍计入持仓估值；确认才减少份额与成本并把净回款转为待到账；到账再从待到账转入现金。已确认的申请不能直接撤销，已到账的确认必须先撤销到账；到账金额必须与待到账一致，不静默抹平差额。

积存金曾使用两步模型：卖出时选择已到账或待到账，待到账结转克数与成本、计入待到账资产，到账时等额转入现金。当前页面已改为卖出默认直接到账；历史 `pendingArrival` 记录继续保留到账接口，不因入口移除而改写，到账金额仍必须与记录一致。

真实行情接入沿用同一行情事实模型：基金净值取天天基金最近已披露值，积存金参考价使用工商银行积存金主动积存价；两者都保存有效日期、来源和取得时间，失败时保留最近有效值并在持仓上记录失败原因。当前页面不再展示积存金来源名称，也不提供手动报价入口；服务端手动报价接口仅保留用于维护和兼容。

自动记账使用计划 + 执行期次模型：每个计划每个周期只生成一个期次，保存金额和计划版本快照；后台按业务日期和固定顺序执行，余额不足整笔待处理。期次以自身标识作为业务 `requestId`，重试不会重复入账；暂停不追补，恢复从下一期继续。2026-10-27 后计划页按基金定投 / 公积金 / 定期收入分组展示，基金定投按基金名称合并 A/C 类别卡片，但执行与去重仍按各份额类别独立处理。

首页趋势按日重放现有事实和有效行情：完整总资产只在四类资产依据齐全时返回，依据不足的日期留空；部分资产合计单独绘制为虚线，不冒充完整总额。趋势只读，不生成业务记录。首页标题中的“总资产 / 已记录资产”则由当前资产覆盖状态自动判定：四类资产均已录入或标记不持有即显示总资产，不再需要手动确认。

2026-10-26 先把前端改为由 API 服务同源托管并使用哈希路由，加上 Render 部署和访问口令；2026-10-27 将明文口令替换为服务端会话 Cookie，并追加 Passkey。认证改造不改变账本业务事实，只改变访问控制和登录体验；Passkey 凭据单独存表，不影响口令兜底。
