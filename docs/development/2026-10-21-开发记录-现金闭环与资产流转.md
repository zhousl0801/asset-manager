### 3.1 请求约定

- 资产变更请求都包含客户端生成的 `requestId`（GUID）。
- 同一账本内 `requestId` 唯一；重复提交返回首次记录，不再次改变现金或持仓。
- 金额两位小数；份额、克数、净值、报价最多四位小数。
- 业务日期不得早于账本起始日期、不得晚于今天；净值 / 报价日期不得晚于今天。
- 现金不足、卖出超过持有数量、份额 / 克数为 0 但成本不为 0 等情况整笔拒绝。

### 3.2 现金页响应口径

`GET /api/ledger/cash` 返回：

- 当前余额与截至日期；
- 月初余额、本月现金流入、本月现金流出、余额调整合计、余额净变动；
- 按日合并的现金变动列表，类型为 `daily`、`assetTransfer`、`adjustment`；
- 资产流转记录带 `assetType`，便于前端跳转到公积金 / 基金 / 积存金页面。

```text
现金净变动 = 现金流入 − 现金流出 + 余额调整
月初余额 = 当前余额 − 本月日常收支影响 − 本月资产流转影响 − 本月余额调整
```

现金流入 / 流出包含日常收支与资产流转，余额调整单独列示，不计入流入或流出。

## 5. 业务规则与不变量

### 5.1 总资产

```text
总资产 = 现金余额 + 基金持仓估值 + 公积金余额 + 积存金持仓估值
基金持仓估值 = Σ(份额 × 最新净值)
积存金持仓估值 = 持有克数 × 当前报价
```

未录入的资产返回“未录入”，不以 0 冒充已确认资产。录入已有持仓、更新净值或报价只改变资产估值，不改变现金。

### 5.2 公积金

- 缴存：个人＋单位合计作为一笔，只增加公积金余额；不计工资或生活收入。
- 提取：金额不得超过可用余额；公积金减少、现金等额增加；总资产不变，生活收支不变。
- 变动列表按业务日期展示，并计算每笔后的公积金余额。

### 5.3 基金

- 买入：现金减少扣款金额，持仓份额与成本增加；成交净值与份额用于估值，金额与估值差额体现在持有收益。
- 卖出：按卖出份额比例结转成本；全部卖出时结转全部剩余成本；净回款进入现金；`已实现收益 += 净回款 − 结转成本`。
- 卖出份额不得超过持有份额；买入扣款不得超过可用现金。
- 净值更新只改变持仓估值，不改变现金和成本。

### 5.4 积存金

- 买入：现金减少实际扣款，克数与成本增加；可同时更新当前报价。
- 卖出：按加权平均成本结转；净回款进入现金；更新已实现盈亏。
- 报价更新只改变估值和持有盈亏，不改变现金、克数和成本。
- 录入 / 核对持仓用于已有持仓或更正；持有克数为 0 时成本必须为 0；不扣现金。
- 当前报价为手动维护，尚未接入真实行情。

### 5.5 余额核对

- 实际余额等于账面余额时提示一致，不生成 0 元调整。
- 存在差额时生成独立调整记录，差额可正可负；只影响现金和总资产。
- 调整后的余额继续作为后续收支、买入校验的基准。
- 调整记录在现金页“余额调整”筛选下单独展示。

### 5.6 一致性

- 单次业务中现金与资产持仓在同一个 `SaveChanges` 中提交，失败整笔不生效。
- 现金账户、公积金账户、基金持仓、积存金持仓均带 `version`；任一并发冲突使整笔失败并返回 409。
- 资产变更使用 `requestId` 防重；`(ledger_id, request_id)` 唯一索引兜底并发重复提交。
- 唯一键冲突与并发冲突统一映射为 409，客户端刷新或重试后可读到首次结果。
- 金额、份额、克数、价格均以服务器端十进制计算，前端只负责展示和提交。

## 8. 已知边界与后续建议

本轮未实现：

- 基金买入待确认、买入确认、赎回申请 / 确认 / 到账的在途状态；
- 积存金卖出待到账与确认收款；
- 真实基金净值、黄金报价和行情更新失败状态；
- 投资分组、组合视角、收益走势、收益日历和分类排行；
- 定投计划、工资 / 缴存 / 提取自动记账与后台任务；
- 截图识别、分类管理、数据导出与完整备份恢复；
- 登录认证、云端部署与多端同步。

当前基金和积存金买卖按“直接成交”处理：买入立即扣现金并增加持仓，卖出立即增加现金并结转成本。后续实现待到账 / 待确认时，应保持同一原则：同一笔资金只能存在于一个资产状态中，不能同时计入现金与在途。

建议下一步优先完善：

1. 基金买入待确认与赎回到账、积存金卖出待到账，补齐在途资产状态；
2. 首页本月变化构成（生活结余、公积金缴存、投资盈亏、核对差额）；
3. 自动记账计划与后台执行；
4. 真实净值 / 报价更新与失败回退；
5. 分类管理、导出与备份恢复。
