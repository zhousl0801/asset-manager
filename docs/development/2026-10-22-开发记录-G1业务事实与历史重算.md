## 1. 已实现行为

### 独立起始日期

- 初始化增加 `cashAsOfDate`，与账本起始日期分开。未指定时以账本起始日期建立现金起点；现金起点之前的现金业务不能在缺乏依据时入账。
- 基金已有持仓和黄金持仓核对必须提供 `holdingDate`，不再把净值 / 报价日期当作持仓日期。
- 公积金支持指定日期的起始余额，既不计为缴存，也不计入生活收入，不改变现金。
- 起始金额、持仓日期、交易日期和行情日期均可在历史核对中更正；更正必须填写原因并先预览。

### 业务事实与重放

`LedgerEntry`、`AssetTransaction`、`CashAdjustment` 保存业务日期、稳定的 `BusinessSequence`、版本及活动 / 撤销状态。账本统一维护 `NextFactSequence`，同日按保存的业务顺序重放；明确更正顺序时同步推进自动分配器，不能依赖随机 ID 或数据库装载顺序。

现有收支、现金核对、公积金、基金和黄金写入均接入重放。计算器依次检查每一时点的现金、公积金余额和可售数量，拒绝负数、超卖或超出金额 / 数量范围的结果；基金和黄金按比例结转成本，金额保留两位小数，全部卖出时清空剩余成本。历史补录会重算后续卖出的剩余成本和已实现收益。

事实、重建后的当前投影、现金核对差额及请求回执由同一次 `SaveChanges` 提交。账本 `Version` 提供统一并发保护，避免不同资产或纯日期更正各自通过后组合成非法历史。校验失败会清除本次暂存变更，不污染下一次请求。

### 实际余额核对与漏记关联

现金核对保存的是当时观察到的**目标余额**。补录核对前的业务后，重新计算该次核对的差额，而不是在核对余额上机械再加减一遍。

普通补录若会改变已有核对差额，要求关联漏记业务，或到历史核对预览并确认。关联字段 `relatedCashAdjustmentId` 可用于生活收支、基金 / 黄金买卖和公积金提取；校验日期不晚于核对日、方向与原差额一致，累计关联金额不超过原始记录差额。同日关联业务在对应核对事实之前生效。

例如现金 1,000 核对为 950，后来找到核对前漏记支出 50：关联保存后现金仍为 950，生活支出增加 50，核对差额从 −50 变为 0。原始差额仍保留，供关联限额校验和审计。

### 行情依据与历史回看

新增 `PriceObservation`，保存价格、有效日期、来源、取得时刻、来源业务事实、修订顺序和是否已被更正。当前估值选择截至查看日期的最近有效行情，同日采用最后有效修订；行情更新不改变数量、成本和现金。

卖出请求没有独立报价事实时，不再把当前缓存价格写作卖出时点的历史价格。更正或撤销行情来源事实会作废关联观察记录，原数据仍保留。删除唯一有效行情后，首页与资产页显示依据不足 / 行情待补，不继续展示缓存估值和相应持有收益。

历史页可选择日期回看现金、公积金、持仓数量 / 成本、估值及行情依据。缺少资产起点、确认日期或有效行情时，完整总资产为空，单列已有依据的部分合计；首页也区分完整总资产与部分资产合计。尚未实现完整趋势图。

## 2. 历史更正流程与接口

| 接口 / 契约 | 本轮变化 |
| --- | --- |
| `POST /api/ledger/initialize` | 可提供 `cashAsOfDate` |
| `POST /api/ledger/funds/positions` | 必须提供独立 `holdingDate` |
| `POST /api/ledger/gold/holding` | 必须提供独立 `holdingDate`，仍校验 `expectedVersion` |
| `POST /api/ledger/provident/opening` | `balance/businessDate/note/requestId`，已有起始记录时通过历史更正处理 |
| 收支新建 / 修改、资产现金流转 | 可提供 `relatedCashAdjustmentId` |
| `GET /api/ledger/history?asOf=yyyy-MM-dd` | 当前账本版本、起始现金、所有日期事实（含撤销）、行情、最近 100 次更正审计及指定日重放结果 |
| `POST /api/ledger/history/preview` | 只读计算更正 / 撤销影响，不写回执、不保存数据库 |
| `POST /api/ledger/history/change` | 提交 `{ change, previewToken }`，通过请求回执提供幂等与响应恢复 |

更正请求包含 `requestId/expectedLedgerVersion/source/factId/expectedFactVersion/action/date/sequence/amount/quantity/price/priceDate/entryKind/category/note/reason/relatedCashAdjustmentId`；`source` 为 `cashOpening/entry/asset/adjustment`，`action` 为 `correct/reverse`。现金核对的 `amount` 表示目标余额。起始现金只能更正，不能撤销。

预览返回变更前后的余额、数量、剩余成本、已实现收益、行情价格 / 有效日、估值、总资产覆盖情况以及各次核对差额。确认使用同一份请求和预览签名：草稿变化、账本有新写入或服务重启后，需要重新预览。预览请求期间修改草稿时，旧响应会被丢弃。

首页、现金页、账本页与资产页均有历史核对入口。收支编辑入口转到统一历史核对，先预览再确认。漏记业务在原录入表单中按需展开核对记录关联；保存结果未知时仍使用 G0 的浏览器待核实请求记录和回执恢复，历史确认请求也纳入同一恢复机制。

## 3. 迁移与已有数据

新增第 7 个迁移 `20261021144121_AddChronologicalHistory`，增加历史事实元数据、独立现金起点、账本并发版本及 `price_observations`。

- 保留原有当前现金、公积金、数量、成本和已实现收益。
- 现金起点由完整收支、资产现金流和原核对差额精确反推；无有效非负起点时标为待确认，不猜金额。
- 旧基金起始持仓及黄金核对快照标为 `NeedsDateConfirmation`；保留原字段供核对，不把原行情日期宣称为已确认的持仓日期。确认前保留该资产的当前缓存显示，阻止相关数量 / 成本变更，无关现金记账仍可进行。
- 旧记录原本已知的行情有效日期予以保留。缓存行情能够匹配原行情事实时，观察记录关联原事实；无法匹配时新增明确注明“迁移保留的最新已知行情”的报价事实，提供更正和撤销入口。所有迁移行情均可追溯到来源事实，不补造过去行情。
- 旧数据的同日顺序按已有创建顺序一次导入并持久化，创建时间相同的使用稳定导入排序；这只是导入顺序，用户仍可明确核对更正，不推断缺失的真实业务时刻。

迁移仅在独立临时 PostgreSQL 测试库验证。现有开发业务库原停留在前 5 个迁移，本轮未应用第 6 / 7 个迁移；连接更新后的 API 前应先备份并执行 README 中的迁移命令。没有进行云端或生产操作。

| 场景 | 结果 |
| --- | --- |
