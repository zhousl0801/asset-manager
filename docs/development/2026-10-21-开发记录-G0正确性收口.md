## 2. 写入、请求恢复与审计

所有正式收支新建、修改、撤销、现金核对和资产变更通过 `MutationExecutor`：

```text
读取账本 → 查 requestId 回执 → 比较操作与内容
→ 业务/历史/版本校验 → 修改现金和资产/记录
→ 添加请求回执 → 同一次 SaveChanges 提交
```

- 同一账本内回执主键为 `(ledger_id, request_id)`，不同业务操作也不能重复占用同一请求标识。
- 指纹对字段顺序、字符串首尾空格和 decimal 表达做规范化；金额、数量、日期、对象、操作类型改变仍视为不同请求。
- 已完成请求返回首次保存结果；其现金余额字段是首次操作结果，当前余额由概览重新读取，不随重试重新计算。
- 现金核对先查回执，再校验 `expectedVersion`，因此原请求的旧版本不阻止安全重放。核对一致时也持久化回执并推进版本，不产生 0 元调整。
- 金额、份额、交易记录、请求结果同事务；唯一键或 version 冲突导致整笔回滚。
- 收支修改/撤销、黄金持仓核对的回执保存变更前状态 `before_json`；与本次请求、结果共同留痕。
- G0 前已存在但没有完整请求快照的旧请求，重复提交时明确提示核对原记录；不推断内容相同，也不重复执行。

前端仅将待核实的请求草稿保存在本机 localStorage，成功确认或明确业务拒绝后清除；这不是离线自动入账。结果未知时保留原请求、阻止改内容或新建另一笔绕过核实。刷新后顶部提供“查询保存结果 / 重试原请求”；重试始终使用原 ID 与原正文，不自动生成新 ID 补交。

## 3. 接口变化

| 接口 | 变化 |
| --- | --- |
| `GET /api/ledger/requests/{requestId}` | 读取已提交请求的操作类型和首次业务结果；未找到返回 404，不能据此断言正在执行的请求最终不会入账 |
| `POST /api/ledger/cash/reconcile` | 必须提供有效 `requestId`；`expectedVersion` 来自现金概览 |
| `GET /api/ledger/cash` | 新增 `version` |
| `POST /api/ledger/gold/holding` | 新增 `expectedVersion`，来自黄金概览；首次未配置为 0 |
| `GET /api/ledger/gold` | 新增 `version` |
| `PUT /api/ledger/entries/{id}` | 新增 `requestId` |
| `POST /api/ledger/entries/{id}/reverse` | 新增 `requestId` |
| `GET /api/ledger/entries` | 新增 `page/pageSize`，默认 1/100，单页最多 200；返回 `page/pageSize/totalCount`；周期汇总不受明细分页和筛选影响，沿用原统计口径 |
| `GET /api/ledger/provident` | 新增 `periodFrom/periodTo` |

核对示例：

```json
{
  "actualBalance": 900.00,
  "reason": "核对",
  "requestId": "a649b299-9ee6-4277-9570-41f897207e97",
  "expectedVersion": 2
}
```

## 7. 仍保留的边界与下一步

- 基金和黄金仍按本轮之前的直接成交方式处理，未实现在途状态、真实行情、自动计划、认证或云端部署。
